# workflow-optimization 概念

這份說明 `workflow-optimization` 為什麼這樣做。SKILL.md 是操作步驟，這裡是背後的想法、量測定義與根因手冊。任何用 Claude Code 開發的專案都適用，不限定 task-workflow。

## 1. 時間花在哪：四種成本

一次對話的掛鐘時間 ＝ **模型生成** ＋ **工具執行** ＋ **等待** ＋ **摩擦**。

| 成本 | 定義（transcript-stats 怎麼算） | 能不能優化 |
|---|---|---|
| 模型生成 | 工具結果回來（或使用者送出）到下一則 assistant 訊息的時間；輸出 tokens 與讀入 context 越大越久 | 能：寫少一點、重寫少一點、context 小一點 |
| 工具執行 | tool_use 到 tool_result 的時間（測試、建置、git、截圖） | 能：修慢的測試、少跑幾次、跑小範圍 |
| 等待 | 等使用者回覆、開會、下班；掛鐘時間遠大於「執行中」時間的部分 | 通常不能，也不該：那是人的時間，不是流程成本 |
| 摩擦 | 沒產出結果的來回：指令被守門擋下、權限拒絕、找不到字串的 Edit、sleep 輪詢、同一檔整份重寫 | 最值得：純浪費，而且常常一個規則就能消掉一大類 |

「執行中」（turn_duration 加總）大約等於模型生成＋工具執行＋摩擦。看流程成本時用它，不要用掛鐘時間。

## 2. 原則

1. **先量後改**：沒有數字的優化只是感覺。先跑統計，前 5 名用數字講。
2. **依時間排名，不依次數**：被擋 100 次但每次只多 4 秒，可能比不上一支每次 25 秒的測試跑 100 次。兩個都看，但排序用時間。
3. **追到根因**：「planner 很慢」是症狀，「一個 planner 循序寫五項、每項整檔重寫八次」才是根因。解法要對準根因。
4. **修在源頭**：能改規則、工具或共用 helper，就不要只修這一次的個案。一條 agent 規則或一支一次做完的腳本，可以消掉整類摩擦。
5. **防再犯**：修正同時加契約測試（例如「所有啟動 Chrome 的地方都帶 keyring 旗標」「agent 定義含某條規則」），下次有人改回去就會紅。
6. **改後再量**：當場量得到的（測試秒數）當場量；只能從下期紀錄看出的（被擋次數、平均掛鐘），寫成有目標值的「下次驗證」假設。
7. **逐期比對**：每次報告都用同一張「指標摘要」表，下次才比得出增減。

## 3. 根因手冊

| 症狀 | 往下挖 | 常見根因 | 典型解法 |
|---|---|---|---|
| 測試總時間高 | 逐檔計時（`node --test` 逐檔、`pytest --durations=10`、spec reporter 看子測試毫秒） | 單一檔卡住：headless Chrome 等 keyring（缺 `--password-store=basic --use-mock-keychain`）、固定 sleep、真的等逾時、每個 test 重啟伺服器或瀏覽器 | 修那一檔的啟動參數，或改成共用 helper 並在 before／after 共用；加防再犯契約 |
| 寫測試／寫程式的 agent 很久、輸出 tokens 高 | 哪些檔被寫很多次、多大；一個 agent 是否包辦多項 | 循序包辦多項；檔案過肥；整檔重寫；反覆跑全套 | 一個 agent 一項、平行派；大小上限；先列斷言再一次寫、之後局部 Edit；迭代只跑本項 |
| 指令被隔離守門擋下 | 依 agent 與指令形狀分布 | 沒有 Write 工具只能用 heredoc；cd、git、管線串成一行；`git -C` 指向共用 checkout | 規則放在 agent 定義最前面；給 Write（限暫存目錄）；把多步驟包成一支腳本一次呼叫 |
| sleep／until 輪詢 | 誰在背景執行後輪詢 | 怕測試跑太久就丟背景 | 前景執行並設 timeout；真的慢就先修慢的測試 |
| 主 session 生成時間高、context 峰值大 | 最大的 session 跨了幾波、幾個 prompt；subagent 回報長度 | 一個 session 做太多事；回報太長；主 session 自己讀大檔 | 一段工作一個 session，結束寫交接紀錄後 `/clear`；回報格式精簡；讀大檔交給 subagent |
| 驗證 agent 很久 | 最久幾次用了哪些工具 | 整頁截圖卡住；手動串乾淨 checkout；重跑太多次 | 一次做完的驗證腳本；截元素不截整頁 |
| Edit 找不到字串、要求先 Read | 錯誤類型分布 | 憑記憶改檔；檔案被別人改過 | 改前先 Read 那一段；多處改動用一次 Write 或腳本 |

## 4. 反模式（不要這樣做）

- **用放寬守門或權限來減少被擋次數**：隔離守門與權限是資安和可追溯的防線。被擋多代表指令寫法要改，不是把防線拆掉。絕不關閉守門、不加寬鬆的 allow 規則來「優化」。
- **把等待時間算成流程成本**：使用者開會、下班的時間不該被「優化」，也不該催使用者。
- **為了變快而放寬驗收**：刪測試、降低斷言、跳過驗證，都不算優化。
- **只改這一次的個案**：下週同樣的問題會換個地方再發生。
- **沒有前後數字就宣稱改善**。

## 5. 資安與隱私

- 對話紀錄（`~/.claude/projects/**`）含使用者原話、指令、檔案內容，可能含憑證。只在本機讀，不外傳。
- 統計與報告只寫數字、工具名、指令的第一個詞與形狀特徵；不抄 prompt、指令全文、檔案內容。
- 需要細看某個 session 時交給 subagent，並要求它只回報統計值與形狀。
